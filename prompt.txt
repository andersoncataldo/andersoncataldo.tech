PROMPT: AUDITORIA COMPLETA PÓS-CORREÇÃO (Portfólio Anderson Viana Cataldo)

CONTEXTO
Este é um portfólio pessoal em React 18 + TypeScript + Vite + Tailwind v4, com
sidebar fixa à esquerda como navegação principal. Um conjunto de correções já
foi aplicado anteriormente (bug de contraste no dark mode, link de navegação
faltando, remoção de código morto, etc.).

Sua tarefa agora NÃO é aplicar aquele prompt de novo. É fazer uma auditoria
NOVA, completa e cética, como se o código nunca tivesse sido revisado antes:
assuma que as correções anteriores podem ter sido parciais, ter introduzido
efeitos colaterais, ou que existam problemas que não foram cobertos da
primeira vez. Verifique também se cada item do prompt anterior foi realmente
resolvido (não confie apenas na existência de um commit dizendo que foi
resolvido — confirme lendo o código).

Percorra literalmente TODOS os arquivos do projeto (componentes, estilos,
configs, tipos, HTML, scripts) antes de concluir. Não pule arquivos pequenos
ou de config assumindo que "não têm erro".

Produza um relatório estruturado (não apenas uma lista solta) com, para cada
problema encontrado: arquivo + linha (ou trecho), descrição do problema,
causa raiz, severidade (Crítico / Alto / Médio / Baixo) e uma sugestão de
correção. Ao final, um resumo com contagem de problemas por categoria e por
severidade.

============================================================
MÉTODO DE AUDITORIA (siga nesta ordem)
============================================================

PASSO 1 — Build e verificação estática
- Rode `npm run build` (tsc -b && vite build) e `npm run lint`. Reporte
  qualquer erro/warning literal, mesmo que pareça inofensivo.
- Procure por: tipos "any" implícitos, imports não usados, variáveis não
  usadas, componentes/funções declarados e nunca chamados, props declaradas
  na interface mas nunca usadas no componente.
- Verifique se existem arquivos órfãos: componentes, hooks, utils ou assets
  que não são importados por nenhum outro arquivo do projeto.

PASSO 2 — Navegação e roteamento interno
- Para cada seção renderizada em src/App.tsx (com seu `id`), confirme que
  existe um link correspondente na sidebar (src/components/Sidebar.tsx) e
  que o href bate exatamente com o id da seção (ex: `#sobre` -> `id="sobre"`).
- Para cada link da sidebar, confirme que o destino (`#algumId`) existe de
  fato em algum elemento do DOM renderizado.
- Verifique se o estado "ativo" (scroll-spy) muda corretamente ao rolar por
  todas as seções, inclusive a primeira e a última, e não trava em um estado
  incorreto quando a página é redimensionada ou quando o usuário clica um
  link e a página ainda está animando o scroll suave.
- Verifique o comportamento em três contextos: sidebar fixa em desktop,
  drawer mobile, e o botão de colapsar/expandir — clique tudo mentalmente
  (ou simule) e veja se algum estado fica inconsistente (ex: menu mobile
  aberto ao redimensionar para desktop, foco perdido ao fechar o drawer).

PASSO 3 — Consistência visual entre temas (claro/escuro)
- Para CADA componente que define cor de fundo, cor de texto ou borda,
  verifique manualmente a combinação resultante em light mode E em dark mode
  usando os valores reais de src/styles/index.css. Procure especificamente
  por:
  - texto e fundo que resolvem para a mesma cor (ou cores muito próximas) em
    qualquer um dos dois temas;
  - classes que misturam tokens dinâmicos (ex: bg-apple-text, que muda com o
    tema) com cores fixas (ex: text-white, text-black) sem tratar o caso em
    que o token muda de lado;
  - elementos com fundo definido mas sem cor de texto explícita, herdando
    uma cor que pode não ter contraste suficiente.
- Verifique se a transição entre temas (toggle) é suave em todos os
  componentes, inclusive nos que são carregados via lazy/Suspense (podem não
  ter recebido o className correto na primeira renderização).

PASSO 4 — Dados e conteúdo
- Compare cada interface em src/types/index.ts com os dados reais
  (src/components/Experience.tsx, Projects.tsx) e com o que é efetivamente
  renderizado em tela. Aponte qualquer campo que exista nos dados mas nunca
  seja exibido, e qualquer campo usado no JSX que não exista no tipo.
- Verifique datas e períodos de experiência (ex: "Jun/2026 - Atual") quanto a
  consistência cronológica (datas de início antes de fim, não sobreposição
  ilógica, ano coerente com a data atual do sistema).
- Verifique se todos os links externos (GitHub, LinkedIn, demos, PDF do
  currículo) apontam para URLs válidas em formato (https://, sem espaços,
  sem barra dupla) e se têm `target="_blank"` acompanhado de
  `rel="noopener noreferrer"`.
- Verifique se e-mail, GitHub e LinkedIn aparecem com o mesmo valor em todos
  os lugares onde são citados (sidebar, contato, rodapé, meta tags) — sinal
  de que a centralização de constantes (se foi feita) está sendo usada de
  fato em todos os pontos, e não apenas em parte deles.

PASSO 5 — Componentes interativos (funcionalidade real)
- CopyEmail.tsx: confirme que o estado "copiado" volta ao normal depois do
  timeout, que falhas de clipboard (navigator.clipboard indisponível, ex.
  contexto não-HTTPS) são tratadas sem quebrar a UI, e que o botão continua
  acessível por teclado (Enter/Espaço).
- Toggle de tema: confirme que o valor salvo no localStorage é respeitado no
  carregamento inicial sem "flash" de tema errado (FOUC), e que alternar o
  tema não reseta outros estados da sidebar (ex: menu mobile aberto,
  scroll-spy).
- Sidebar mobile (drawer): confirme que o focus trap continua funcionando,
  que Esc fecha o menu, que o scroll do body é restaurado ao fechar, e que
  não há como tabular para elementos "atrás" do overlay enquanto ele está
  aberto.
- Botão de colapsar sidebar (desktop): confirme que nenhum conteúdo fica
  cortado, sobreposto ou ilegível no estado colapsado, e que o aria-label do
  botão muda corretamente entre "Expandir" e "Recolher" conforme o estado.

PASSO 6 — Responsividade
- Avalie o layout nos breakpoints usados pelo projeto (mobile ~375px,
  tablet ~768px, desktop ~1024px+, e o breakpoint `lg` do Tailwind onde a
  sidebar deixa de ser drawer). Procure por:
  - texto cortado, sobreposição de elementos, scroll horizontal indesejado;
  - áreas clicáveis menores que 44x44px em botões/links importantes;
  - grids que quebram mal em telas intermediárias (ex: 2 colunas viram 1
    coluna larga demais, ou ficam apertadas antes da hora).
- Verifique se o `main` sempre recebe o padding-left correto correspondente
  ao estado da sidebar (aberta/colapsada) em cada breakpoint, sem sobra de
  espaço em branco nem conteúdo escondido atrás da sidebar fixa.

PASSO 7 — Acessibilidade (a11y)
- Verifique se todo elemento interativo (botão, link, input) tem nome
  acessível (texto visível, aria-label ou aria-labelledby).
- Verifique a ordem de tabulação (tab order) da página inteira, incluindo
  sidebar, conteúdo principal e footer — deve seguir uma ordem lógica visual.
- Verifique se há pelo menos um heading `<h1>` por página e se a hierarquia
  de headings (h1 > h2 > h3) é sequencial, sem pular níveis.
- Verifique se `aria-current`, `aria-expanded`, `aria-hidden` e `role` são
  usados corretamente e refletem o estado real do componente (não estáticos
  quando deveriam mudar dinamicamente).
- Verifique se `prefers-reduced-motion` é respeitado nas animações do
  framer-motion, caso a correção correspondente tenha sido implementada —
  confirme que ela realmente desativa/reduz o movimento e não é apenas
  cosmética.

PASSO 8 — Performance e carregamento
- Verifique se os componentes lazy-loaded (About, Experience, Automation,
  Skills, Projects, Contact, Footer) não causam layout shift perceptível
  quando entram (compare com e sem o fallback do Suspense).
- Verifique se imagens têm dimensões explícitas (width/height ou
  aspect-ratio) para evitar CLS, e se usam `loading="lazy"` apenas quando
  fora da primeira dobra.
- Verifique o tamanho e formato dos assets (imagem de perfil, PDF do
  currículo) e se há algum asset não utilizado ainda incluso no bundle.
- Verifique se não há chamadas, listeners ou observers (scroll, resize,
  IntersectionObserver) criados sem a devida limpeza (cleanup) no
  useEffect, o que causaria vazamento de memória ou comportamento
  duplicado ao navegar/re-renderizar.

PASSO 9 — SEO e metadados
- Verifique se index.html tem title, description, canonical, Open Graph e
  Twitter Card preenchidos corretamente e com valores plausíveis (não
  genéricos/placeholder).
- Verifique se o favicon carrega corretamente e não é mais o ícone padrão do
  Vite/React.
- Verifique se public/robots.txt e public/sitemap.xml (caso existam) estão
  com sintaxe válida e URLs corretas.
- Verifique se algum dado estruturado (JSON-LD), se implementado, é um JSON
  válido e reflete os dados reais do site (nome, links).

PASSO 10 — Higiene de repositório
- Verifique .gitignore quanto a arquivos de build que não deveriam ser
  versionados (*.tsbuildinfo, dist, node_modules, .env).
- Verifique se ainda existem arquivos mortos, duplicados ou renomeações
  pendentes (ex: assets com espaço no nome, componentes não referenciados).
- Verifique se README.md está atualizado e reflete o estado real do projeto
  (seções existentes, scripts, notas de design) — aponte qualquer
  divergência entre o que o README descreve e o que o código realmente faz.

============================================================
FORMATO DE SAÍDA ESPERADO
============================================================

1. Resumo executivo (3-5 linhas): estado geral do projeto, se está pronto
   para produção ou não, e os problemas mais urgentes.

2. Tabela ou lista de problemas encontrados, agrupados por categoria (Build/
   Tipagem, Navegação, Temas/Contraste, Dados/Conteúdo, Interatividade,
   Responsividade, Acessibilidade, Performance, SEO, Repositório), cada um
   com:
   - Arquivo e localização
   - Descrição do problema
   - Severidade (Crítico / Alto / Médio / Baixo)
   - Sugestão objetiva de correção

3. Checklist de confirmação dos itens do prompt de correção anterior,
   indicando para cada um: Resolvido / Parcialmente resolvido / Não
   resolvido / Não verificável, com justificativa curta.

4. Contagem final de problemas por severidade e recomendação de próximos
   passos priorizados.

============================================================
REGRAS IMPORTANTES
============================================================
- Não presuma que algo está correto só porque "parece" ter sido corrigido —
  leia o código-fonte atual antes de concluir qualquer item.
- Não ignore arquivos de configuração (tsconfig*, vite.config.ts,
  eslint.config.js, postcss.config.js, package.json) — erros de configuração
  também são bugs.
- Se um problema já havia sido listado na auditoria anterior e ainda existir,
  reporte de novo (não assuma que "já foi visto, não precisa repetir").
- Se encontrar um problema novo, não coberto por nenhuma auditoria anterior,
  destaque isso explicitamente no relatório.
- Não aplique correções nesta etapa — apenas audite e relate. A aplicação
  das correções deve ser um passo separado, após revisão do relatório.
